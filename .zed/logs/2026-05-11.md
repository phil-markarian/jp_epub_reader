## Risk review

### High

- Persisted library paths are trusted too broadly.
  `src-tauri/src/state.rs` backfills `meta.json` `epub_path` values directly
  into the DB if the file exists. Those persisted paths are later used verbatim
  by:
  - `src-tauri/src/commands/import.rs:227` (`read_epub_bytes`)
  - `src-tauri/src/commands/import.rs:244` (`open_path`)
  - `src-tauri/src/commands/import.rs:148` delete fallback branch

  That means a stale or crafted sidecar can point the app at files outside the
  managed library root. The current implementation does not enforce "library
  files must stay under app data dir / library".

### Medium

- Delete is not transactional and silently discards file cleanup failures.
  `delete_library_entry` best-effort deletes files, ignores any filesystem
  error, and then removes the DB row anyway. Result: orphaned files on disk
  with no library entry.

- Library pagination can strand the user on an empty page after deletions.
  The frontend keeps the old `lib_page` after a delete refresh. If the user
  deletes the last item on the last page, the library panel can render empty
  even though earlier pages still have entries.

- Search results can race and show stale data.
  The search UI fires async IPC lookups on every input change and applies the
  latest response that arrives, not the latest request that was issued.
  Because search is local this is probably intermittent, but the race exists.

### Low / structural

- The documented window-boundary security model is ahead of the current repo
  enforcement.
  Commands are globally registered in `src-tauri/src/lib.rs`, while the visible
  capability files are still basic. Reader vs main-window scoping is described
  in docs, but not yet obviously enforced in code at the command boundary.

- Runtime hardening is still loose relative to the architecture doc.
  `src-tauri/tauri.conf.json` currently has `withGlobalTauri: true` and
  `csp: null`, so the reader/content trust boundary should not be treated as
  hardened yet.

## What to build next

Do not jump straight to dictionary popup or Anki.

The next best milestone is a Phase 3.5 hardening pass:

- Normalize and validate library paths under the managed library root
- Reject or rewrite unsafe backfilled paths
- Make delete behavior transactional or explicitly partial-failure aware
- Clamp/reset library pagination after mutations
- Add request-order protection to search
- Tighten reader/main window command boundaries

After that, start Phase 4 for real:

- vocab schema
- encounter logging
- minimal inspection/review UI

Reasoning: the current app already has a usable import/read path, but it does
not yet have the durable study-data model that the rest of the product depends
on. Hardening the existing slice first reduces risk before building vocab and
review features on top of it.
